この fork を育てていくうえでの考え方。**AI も人も、迷ったらここに戻る。**
ここに書いていないことで判断が分かれたら、推測で決めずにユーザーに聞き、決まったらこの文書に追記する。

## 1. 何のための道具か

コードベースの「どのファイルが、どのファイルの何を使っているか」を一枚の図で見せ、**初めて読むコードや久しぶりに触るコードの全体像を素早くつかむ**ための道具。

- 図は**読むためのもの**。線が出ていれば、そのつながりは実際にあると信じてよい状態を目指す
- 大きなリポジトリでも読めること。フォルダを畳んだ状態から始め、見たいところだけを開く（本家から受け継いだ「collapse-first」の考え方）

| 優先度 | 言語 | 方針 |
|---|---|---|
| 主 | **Python** | 書き方の網羅と正確さに投資する |

## 3. 製品の原則

### 3.1 誤った線を出さない（正確さ ＞ 網羅）
**「つながっていないのに線が出る」は「つながっているのに線が出ない」より悪い。** 誤った線が混ざると、図全体が信用できなくなるため。

- 確信が持てない参照は線にしない。抜けは「既知の限界」として README やテストに書いて残す
- 新しい解決ルールを足すときは、**誤検出の例も fixture に入れて**「線が出ないこと」をテストする（例: コメント内の import、文字列内の型名、使っていない `using`）
- 実行時に決まるもの（`{Binding Foo}`、命名規則による自動結び付け、文字列で組み立てる動的 import など）は線にしない

**この原則に反している既知の箇所（直す対象）**
- C# の型の解決は字面で判断するので、型と同じ名前のプロパティやローカル変数があると、型への線として数える（`extension/src/csResolve.ts`）

### 3.2 解析は静的に、手元だけで
- 解析のためにユーザーのコードを実行しない。ビルドも要求しない
- コードや解析結果を外部に送らない

### 3.3 人が書いたものを上書きしない
- 自動生成の説明文が、ユーザーが手で書いた説明を上書きすることはない（本家の不変条件。`__doc__/README.md`）

### 3.4 Windows と Ubuntu（WSL）の両方を一級の環境として扱う
- 開発者が使う環境は **Windows** と **Ubuntu（WSL）** の2つ。どちらでも同じように動くことを前提にする
- Windows では、パス区切り、ドライブ名の大文字・小文字、大文字・小文字を区別しないファイルシステムで、これまで何度もバグが出た
- WSL では、VS Code の Remote - WSL 経由で拡張機能が Linux 側で動く。**プロジェクトは WSL 側（`/home/...`）に置くことを前提にする**
- Windows 側のフォルダを WSL から `/mnt/c/...` で開くのは、たまにある程度。壊れずに動けばよく、速度などの作り込みはしない（大文字・小文字を区別しない点は、Windows と同じ仕組みで対応済み）
- CI は Windows と Ubuntu の両方で通す。WSL 上の VS Code で画面が動くかは AI には確かめられないので、WSL 固有の処理を変えたときだけ、何を確認してほしいかを具体的に書いて人に頼む

## 4. 技術の方針

### 4.1 解析の仕組み
- 今は正規表現ベースの軽い解析。速く、依存が少ない
- **3.1 の正確さを満たせない場合は、本格的な構文解析器の導入を検討する**（tree-sitter、TypeScript コンパイラ API、Roslyn など）。最初の候補は、上に挙げた C# の誤検出
- 導入するときの条件（案。導入時にユーザーと確定する）
  - 拡張機能に同梱でき、ユーザーに追加のインストールを求めない
  - 大きなリポジトリでも初回の表示が待たされない。基準は、導入前に `tools/` で計測して決める
  - 解析器が使えないときも落ちず、軽い解析に戻るか、その言語の線を出さないで済む
- 正規表現で続ける部分も、コメントや文字列を空白に置き換えてから探す（`blankJsComments`、`blankCsCode`、`blankXmlComments`）

### 4.2 テストできる形に切り出す
- `vscode` に依存しない処理は別ファイルに切り出す（`pyResolve.ts`、`csResolve.ts`、`xamlResolve.ts`、`aliases.ts`、`porcelain.ts`）
- 解析全体は `vscode` のスタブで丸ごとテストできる（`tools/vscode-stub.cjs`、`fixtures/`）

## 5. 開発の進め方（AI ファースト）

**AI が「再現 → 修正 → 検証（画面確認まで）」を自分で回す。** 人に確認を頼むのは、VS Code 本体との連携（ファイルを開く、保存で再描画、LSP、設定画面）を**変えたときだけ**。そのときは PR の報告に、何をどう確かめてほしいかを具体的に書く。それ以外の変更では人に作業を求めない。

1. 問題を `fixtures/` のサンプルで再現する（`node tools/edges.mjs` で今の結果を見る）
2. 期待値をテストに書き、**修正前に失敗することを確かめる**
3. 修正して `npm run verify`
4. 画面に関わるなら `npm run snapshot` で撮って、画像を見て確かめる
5. このPCにある実際のプロジェクトにも `tools/edges.mjs` を当てる（読むだけで、書き換えない）。サンプルでは見つからない問題が出る
6. ブランチを切り、PR を出し、CI（Windows / Ubuntu）が通ったことを確認して報告する。マージはユーザーが行う
7. 新しく分かった落とし穴は `CLAUDE.md` に、判断の基準はこの文書に追記する

- PR は1つの目的に絞り、小さく保つ
- 報告には「確認したこと」と「確認できていないこと・限界」を必ず分けて書く

## 6. 本家との関係

**本家（Ahsaniat/code-canvas）からは独立して育てる。**

- 本家との互換性や、本家へ PR を出せる形にこだわらない。作り替えが必要なら作り替える
- 本家の新しい修正は、内容を見て、役に立つものだけを取り込む（`upstream` リモートは残す）
- 拡張機能 ID は将来、`extension/package.json` 自体を fork 用に変える（今は `npm run install:local` がインストール用のコピーだけを書き換えている）

## 7. 言葉

- 文書・コミット後の報告・PR の説明は日本語
- **コードのコメントは、新しく書く部分・書き換える部分は日本語**。既存の英語のコメントは、そのコードに手を入れるときに必要に応じて書き換える（一括での翻訳はしない）
- コミットメッセージは、これまでどおり英語の短い要約に続けて本文を書く形でよい（`git log` の一覧で読みやすいため）。日本語にしたくなったら、ここを更新する
